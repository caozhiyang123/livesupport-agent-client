# Requirements Document

## Introduction

LiveSupport Web Chat is a minimal web chat interface that lets a browser user exchange messages with an AWS Bedrock AgentCore Runtime agent named `livesupport-agent`. A Python/FastAPI backend sits between the browser and AgentCore Runtime: it receives chat requests over HTTP, invokes the agent runtime via boto3 using IAM (SigV4) credentials from an EC2 instance role, and streams the agent's response back to the browser over Server-Sent Events (SSE). The browser never calls AgentCore directly. The MVP has no application-level login and no server-side conversation persistence; multi-turn context is carried by a frontend-generated session id combined with AgentCore Memory.

## Glossary

- **Backend**: The FastAPI application (`app.py`) that receives browser HTTP requests, invokes AgentCore Runtime via boto3, and streams responses back as SSE.
- **Agent_Client**: The module (`agent_client.py`) that encapsulates the boto3 `bedrock-agentcore` client call to `invoke_agent_runtime` and parses the streamed response.
- **AgentCore_Runtime**: The AWS Bedrock AgentCore Runtime hosting the agent identified by `AGENT_RUNTIME_ARN`.
- **Frontend**: The static browser client (`static/index.html` and `static/chat.js`) that renders the chat UI and consumes the SSE stream.
- **Chat_Endpoint**: The backend HTTP endpoint `POST /api/chat` that accepts a chat message and returns a streamed SSE response.
- **Session_Id**: A UUID string of at least 33 characters generated by the Frontend for each conversation, passed to AgentCore_Runtime as `runtimeSessionId`, used to route requests to the same underlying microVM and to correlate multi-turn context in AgentCore Memory.
- **Payload**: The JSON object sent to AgentCore_Runtime, containing the field `prompt` holding the user's message text, with the field name centrally defined in configuration/constants.
- **Instance_Role**: The EC2 instance profile role that grants `bedrock-agentcore:InvokeAgentRuntime` permission scoped to the AgentCore_Runtime ARN, supplying credentials via the default boto3 credential chain.
- **Rate_Limiter**: The backend component that restricts the number of Chat_Endpoint requests accepted per client within a defined time window.
- **New_Conversation_Control**: The Frontend UI control that discards the current Session_Id and generates a new one.

## Requirements

### Requirement 1: Chat message submission

**User Story:** As a website visitor, I want to type a message and send it to the support agent, so that I can get a response without leaving the page.

#### Acceptance Criteria

1. WHEN a user submits a non-empty message through the Frontend, THE Frontend SHALL send an HTTP POST request to the Chat_Endpoint containing the message text and the current Session_Id.
2. IF a user submits an empty or whitespace-only message, THEN THE Frontend SHALL prevent the request from being sent to the Chat_Endpoint.
3. WHEN the Chat_Endpoint receives a request, THE Backend SHALL construct a Payload with the message text under the configured field name and invoke AgentCore_Runtime through Agent_Client.
4. WHEN Agent_Client invokes AgentCore_Runtime, THE Agent_Client SHALL pass the AgentCore_Runtime ARN, the Session_Id as `runtimeSessionId`, the Payload as JSON-encoded bytes, and the qualifier `DEFAULT`.
5. THE Agent_Client SHALL execute the boto3 `invoke_agent_runtime` call inside a thread pool executor so that the FastAPI event loop is not blocked.

### Requirement 2: Streaming response delivery

**User Story:** As a website visitor, I want to see the agent's reply appear progressively, so that I perceive the assistant as responsive.

#### Acceptance Criteria

1. WHEN AgentCore_Runtime returns a `text/event-stream` response, THE Agent_Client SHALL parse each `data:` prefixed line from the response stream.
2. WHEN a parsed `data:` line contains JSON-encoded string content, THE Agent_Client SHALL decode the content before forwarding it.
3. WHEN Agent_Client produces decoded content chunks, THE Backend SHALL forward each chunk to the Frontend as an SSE event over the Chat_Endpoint response.
4. WHEN the Frontend receives an SSE chunk, THE Frontend SHALL append the chunk to the currently rendered agent response text.
5. WHEN AgentCore_Runtime signals the end of the response stream, THE Backend SHALL close the SSE response to the Frontend.

### Requirement 3: Session identity and continuity

**User Story:** As a website visitor, I want my conversation to maintain context across multiple messages, so that I do not have to repeat information.

#### Acceptance Criteria

1. WHEN the Frontend loads without an existing active Session_Id, THE Frontend SHALL generate a new Session_Id as a UUID string of at least 33 characters.
2. WHILE a Session_Id is active, THE Frontend SHALL include that same Session_Id in every Chat_Endpoint request for the current conversation.
3. WHEN a user activates the New_Conversation_Control, THE Frontend SHALL generate a new Session_Id and SHALL use it for all subsequent Chat_Endpoint requests.
4. THE Backend SHALL pass the Session_Id received from the Frontend to AgentCore_Runtime as `runtimeSessionId` without modification.
5. IF a Chat_Endpoint request does not include a Session_Id of at least 33 characters, THEN THE Backend SHALL reject the request with an error response and SHALL NOT invoke AgentCore_Runtime.

### Requirement 4: AWS authentication and configuration

**User Story:** As an operator, I want the backend to authenticate to AgentCore Runtime using the EC2 instance's IAM role, so that no long-lived credentials need to be managed.

#### Acceptance Criteria

1. THE Backend SHALL obtain AWS credentials through the default boto3 credential chain, relying on the Instance_Role when deployed on EC2.
2. THE Backend SHALL read the AgentCore_Runtime ARN and AWS region from environment configuration (`AGENT_RUNTIME_ARN`, `AWS_REGION`) at startup.
3. IF the AgentCore_Runtime ARN or AWS region configuration is missing at startup, THEN THE Backend SHALL fail to start and SHALL log a configuration error.
4. THE Agent_Client SHALL configure the boto3 client's read timeout to a value greater than the default 60-second timeout to accommodate streamed agent responses.
5. THE Backend SHALL use the same AWS region for the boto3 client as the region in which AgentCore_Runtime is deployed.

### Requirement 5: Error and timeout handling

**User Story:** As a website visitor, I want to see a clear message when something goes wrong, so that I understand the chat is temporarily unavailable rather than silently failing.

#### Acceptance Criteria

1. IF the boto3 `invoke_agent_runtime` call raises a client or service error, THEN THE Backend SHALL return an error response to the Frontend without exposing internal stack traces.
2. IF the boto3 `invoke_agent_runtime` call times out, THEN THE Backend SHALL return a timeout error response to the Frontend.
3. WHEN the Frontend receives an error response from the Chat_Endpoint, THE Frontend SHALL display a user-visible error message in the chat interface.
4. IF the SSE connection to the Frontend is interrupted before the stream completes, THEN THE Frontend SHALL display an indication that the response was incomplete.
5. IF boto3 does not provide the `bedrock-agentcore` client (minimum supported version not met), THEN THE Backend SHALL fail to start and SHALL log a dependency version error.

### Requirement 6: Abuse protection

**User Story:** As an operator, I want to limit how frequently a single client can send chat requests, so that the service is protected from abuse given there is no login.

#### Acceptance Criteria

1. THE Rate_Limiter SHALL limit the number of Chat_Endpoint requests accepted from a given client within a configured time window.
2. IF a client exceeds the configured request rate, THEN THE Backend SHALL reject the excess Chat_Endpoint requests with an error response indicating the rate limit was exceeded.
3. THE Backend SHALL apply the Rate_Limiter check before invoking AgentCore_Runtime.

### Requirement 7: Web page delivery

**User Story:** As a website visitor, I want to load the chat page in my browser, so that I can start a conversation with the support agent.

#### Acceptance Criteria

1. WHEN a browser sends an HTTP GET request to the root path `/`, THE Backend SHALL return the chat page HTML.
2. THE Backend SHALL serve the static JavaScript and any supporting static assets required to render and operate the Frontend.

### Requirement 8: Deployment configuration

**User Story:** As an operator, I want the service deployed behind a reverse proxy over HTTPS with correct streaming behavior, so that chat responses stream reliably to real users.

#### Acceptance Criteria

1. WHERE the Backend is deployed on Ubuntu with nginx as a reverse proxy, THE deployment configuration SHALL disable proxy buffering for the Chat_Endpoint so streamed chunks are forwarded without delay.
2. WHERE the Backend is deployed behind nginx, THE deployment configuration SHALL set a proxy read timeout longer than the expected maximum agent response duration.
3. WHERE the Backend is deployed on EC2, THE deployment configuration SHALL restrict inbound security group rules to ports 80 and 443.
